Our approach

Build less, build it right

Every line of custom code is something to test and maintain. The best extension is often the one you don’t need.

  • Fit check first. Standard setup, an AppSource app or a custom extension: we compare cost and upkeep with you.
  • Written specification. You approve what will be built, and the price, before work starts.
  • Built for updates. Microsoft’s extension model, events and APIs only. No changes to base code.
  • Tested and documented. Tested against realistic data and Microsoft’s release previews, with notes your team can read.
  • Your code, your repository. We recommend keeping the source in a repository your company controls.
Worked example · Illustrative scenario

A custom pallet label for a distributor

A distributor prints pallet labels from a separate program and types order details into it by hand. Mislabeled pallets cause returns from two large retail customers.

StageWhat happens
SpecAgree label content per customer: order number, PO, ship-to, carton count and a scannable code.
BuildAn AL extension adds a label layout and a Print Pallet Label action on warehouse shipments.
TestPrint labels for real orders and scan them with the customers’ required formats.
DeployInstall in production after the test sign-off, with a one-page guide for the shipping team.

Outcome: Labels print straight from the shipment with no retyping, and label-related returns stop.

This example shows how we approach this kind of project. It is not a client case study.

In depth

How we decide whether something needs custom code

Every customization has a cost beyond the build: it must be tested with each Microsoft update, documented and maintained. Before writing code we work through a simple order of preference.

  1. Standard setup. Many requests are solved by settings, workflows, approval rules, report layouts or personalization that already exist in Business Central.
  2. Power Platform. Notifications, approvals and simple automations often fit Power Automate without touching Business Central’s code.
  3. An AppSource app. For common needs such as EDI, shipping, scanning or sales tax, a maintained app from a specialist publisher is usually cheaper over time than custom code.
  4. A custom AL extension. For processes that are genuinely specific to your business and worth automating.

What a good extension project includes

A short written specification you approve, a fixed price for that scope, development in a sandbox, testing with your real data, a deployment plan, and documentation your team can read. Source code should live in a repository your company controls, so future developers can pick it up.

Common extension requests

  • Extra fields on customers, items or orders, shown where your team needs them.
  • Custom document layouts: invoices, packing slips, pallet and shelf labels.
  • Validation rules that stop common mistakes before a document posts.
  • Automated jobs, such as nightly price updates or stock exports to a partner.
  • API endpoints for an integration that has no ready-made connector.

We also review extensions written by others before you rely on them, checking for risky code, missing tests and anything that might break with the next Microsoft update.

FAQ

Frequently asked questions

Have a different question? Ask directly.

Will custom extensions break when Business Central updates?

Extensions built on Microsoft’s extension model don’t change Business Central’s own code, which makes updates far safer than old-style customizations. We still test every extension against Microsoft’s release previews before each major update.

Who owns the code?

You should. We recommend keeping your extension source code in a repository your company controls, such as Azure DevOps or GitHub, so you’re never locked in to one developer.

Can you take over extensions someone else wrote?

Yes. We review the code first, fix anything risky and document what it does before making changes.

Do you build AppSource apps?

Our focus is extensions for your company (per-tenant extensions). If your idea would help many Business Central customers, we can talk about what publishing on AppSource involves.
